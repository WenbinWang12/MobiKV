## 0. 研究问题（一句话）

移动用户的多轮 LLM 会话在边缘节点之间切换时，会话的 KV 状态是一个**持续增长、可重建（重算）、可搬运（传输）**的对象。
每次切换都要决定：在原节点远程服务（HOLD）、搬运（transfer）、重算（recompute），还是**同时搬运和重算（hybrid）**；
并且可以利用**用户思考时间**在关键路径之外提前复制（make-before-break）。
我们问：(i) 这些选择由什么量决定；(ii) 能否设计一个在线控制器，在真实移动轨迹和真实对话到达下，稳定降低切换后首 token 时延（TTFT）。

与已有结论的关系：S3 已证明"在关键路径上提前付费"的跨轮规划在实测域无收益。本协议**不重新检验**这一点；
新机制只在关键路径之外（思考时间、空闲链路、空闲 GPU）移动状态，代价是资源而不是时延，因此是不同的问题。

## 1. 无量纲量

- 传输/重算比 ρ = T_tx / T_rc：把同一段缺失 KV（Δ 个 token，前缀长度 s）在目标端准备好，传输与重算各自所需时间之比。
- 理论预言（Prop. 1，见 §5）：并行混合修复把就绪时间降到 T_rc·T_tx/(T_rc+T_tx)（忽略固定开销），
  相对最好单一路径的加速比为 1 + min(ρ, 1/ρ) ∈ (1, 2]。

### 2.1 CT-H 格子（按 ρ 预期落点预先选定，不看数据后增删）
- H1：7B，首次放置 s=0，L=8k，g=25%，无限速
- H2：7B，首次放置 s=0，L=16k，g=25%，无限速
- H3：7B，增量 s=16k，Δ=4k，g=25%，无限速
- H4：7B，首次放置 s=0，L=16k，g=50%，无限速
- H5：7B，首次放置 s=0，L=8k，g=100%，300 Mb/s（预期 ρ≫1，作为"混合无益"的对照）
- 每次混合试验后，从组装好的缓存贪心解码 32 个 token，与目标端完整重算后的解码对照；报告逐 token 一致率（不作门槛，bf16 下近并列翻转是已知现象，见 G1-M）。

### 2.2 预测（冻结）
- P-CT1：g=100%、带宽 ≤0.92 Gb/s 时，所有实测格 ρ > 1（与 Pilot v3 一致）。
- P-CT2：g=25%、无限速时，7B 的完整重算格 ρ 落在 [0.5, 2.5]。
- P-CT3：批量解码 ITL(b=4)/ITL(b=1) ≤ 1.3；FIFO 轮转（ReState 旧引擎）约为 b 倍（已有数据 42/89/140 ms）。
- P-CT4（主要 GPU 主张）：在实测 ρ ∈ [0.5, 2] 的 CT-H 格中，x* 处的就绪时间 ≤ 0.8 × 最好单一路径（加速 ≥1.25×），
  且实测与 Prop.1 预测之差 ≤ 15%。H5 中混合相对最好单一路径的收益 < 5%。
- 判定：P-CT4 在至少 2 个 ρ∈[0.5,2] 格成立 → "混合修复"作为论文机制保留；否则只报告为负结果。

## 3. 轨迹驱动评估（134 CPU）

### 3.1 输入（全部为公开真实数据 + 明确标注的模型）
- 移动：Microsoft GeoLife 1.3 GPS 轨迹（182 用户，北京）。边缘节点为覆盖研究区域的六边形小区，半径 r ∈ {300, 500, 1000} m（默认 500）；
  用户在请求时刻所在小区即服务边缘。GeoLife 有交通方式标注的用户用于分层（步行/骑行/车辆/地铁）。
- 对话：Mooncake FAST'25 conversation_trace（12,031 条请求，1 小时）。用 512-token 块哈希的前缀链重建会话（实现见 code/），
  得到每轮的到达时刻、输入长度、输出长度；轮间间隔中位 126 s。重建方法是启发式的，论文中如实说明。
- 成本：全部来自 §2 的实测拟合；10 Gb/s 等未实测带宽档只作敏感性外推并标注。
- 留出：GeoLife 用户按 ID 7:3 分成训练/测试（移动预测器只用训练用户）；Mooncake 前 30 分钟用于调参，后 30 分钟用于评估。
  控制器的所有参数只在调参段确定，评估段不再改动。

### 3.2 系统模型
- E 个边缘节点，每个 1 块 GPU（算力份额 g_e，默认 25% A100 ≈ L4 级），KV 容量 M_e，持续批处理解码（ITL 按 CT-D 拟合），
  prefill/修复按优先级排队（前景 > 修复 > 后台复制），边缘间链路按每节点上行/下行容量共享（默认 1 Gb/s）。
- 动作：本地命中、HOLD（原节点远程服务，加往返时延）、修复（重算 / 传输 / 混合）、后台复制（KV 模式走链路；token 模式走目标 GPU 空闲周期）、驱逐。

### 3.3 策略
- B1 Anchor：会话固定在首个节点，始终 HOLD。
- B2 Follow-Recompute / B3 Follow-Transfer：切换后首个请求在新节点按需重算 / 传输（关键路径上）。
- B4 Reactive-Best：每个请求在当前成本下选 HOLD / 本地化中耗时最小者（即 S3 的 myopic，带混合修复）。
- B5 Follow-Background：检测到切换后立即在后台迁移，迁移完成前用 HOLD 服务（最强的被动基线）。
- B6 Replicate-Neighbors：每轮结束把增量 KV 推送到所有相邻节点。
- MobiKV（本文）：按需路径同 B4；思考时间内按 "预测到达概率 × 可避免的修复代价 / 资源代价" 选择复制目标与模式（KV/token/混合），
  用 Lyapunov 虚拟队列约束长期链路与 GPU 后台预算；驱逐按同一价值密度。
- Oracle：已知每个会话下一轮的到达节点与时刻，在同样的资源约束下复制（上界参考，不是可部署策略）。
- 公平性：所有基线使用同一成本模型和同一混合修复实现，差异只来自决策。

### 3.4 指标与主张（冻结）
- 主指标：评估段**多轮续接请求**的 TTFT p95；次指标：均值、p99、TTFT ≤ 2 s 的 SLO 达成率、链路字节、后台 GPU 秒、显存占用。
- C-E2E（主张）：默认场景下 MobiKV 的 p95 TTFT ≤ 0.8 × B4 与 B5 中较好者，会话级 bootstrap 95% CI 不含 1。
- C-ROBUST：在 ρ 档（g × 带宽）、移动速度（小区半径、交通方式）、负载、显存预算的单因素扫描中，MobiKV 的 p95 TTFT 从不比该扫描点最好的基线差 5% 以上。
- C-REGIME：报告每个扫描点的最优基线，画出"优势区间图"（回应用户的问题：传输效率与计算效率之比决定哪种动作占优）。
- 任何主张不成立就照实写为不成立，不改指标、不改场景。

## 5. 理论（随论文给出证明）
- Prop. 1（混合修复最优分割）：T_r(x)=a_r+x·R 递增、T_t(x)=a_t+(1−x)·X 递减、并行就绪时间 max(T_r,T_t)，
  最优 x* = clip((X+a_t−a_r)/(R+X), 0, 1)；内点时 T* = (R·X + a_r·X + a_t·R)/(R+X)；a_r=a_t=0 时加速比 1+min(ρ,1/ρ)。
  推广：T_r 凸递增（含注意力二次项）时 x* 为唯一交点，二分可求。
- Prop. 2（按需路径的逐请求最优）：资源状态给定时，逐请求选 min 就绪时间即最优（S3 实测已支持）。
- Thm. 3（后台复制的 drift-plus-penalty）：在有界成本、平稳遍历的到达/移动过程下，长期链路与后台 GPU 预算约束满足，
  期望收益与最优平稳随机策略相差 O(1/V)，虚拟队列积压 O(V)（Neely 2010 框架）。
